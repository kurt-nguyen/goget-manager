# Implementation Plan: Install / Uninstall from the package Detail tab

Scope: replace the Install/Uninstall stub in the Detail tab with a real action. Install runs `go get` in a workspace folder, Uninstall runs `go mod edit -droprequire`. The Detail button, the Installed view and the Search "Installed" badge then follow go.mod, which is already their single source of truth. No new commands, menus or `package.json` changes. No new dependencies. Do NOT push. Coders commit locally with explicit `git add <paths>` (never `.agents/`, never `sample-pages/`).

This is one cohesive change along a single pipeline (runner -> actions -> controller -> webview), each stage needing the previous one's types. It was not split into FEATs; the existing implement/review loop runs it as-is. Gate file for the loop stays `.agents/tasks/install-uninstall-review.json` (`verdict` = `APPROVED`).

## 1. Findings from exploration (code actually read)

### Requirement -> existing mechanism

| Requirement bullet | Already exists | What this plan adds |
|---|---|---|
| install the package | Nothing runs `go`. `grep child_process src` finds nothing. `DetailController.requestInstall()` only logs `installStubLog(...)` ("not implemented yet"). | A Go runner, a pure `PackageActions` service, controller wiring. |
| hide Install, show Uninstall | `detail.ts` shows one `#detail-action` button; label comes from `model.installed` (`setInstalledButton`). `installed` is recomputed from go.mod by `DetailController.computeInstalled` on page settle and on `refreshInstalled()` (called from `extension.ts` via `repository.onDidChange`). | In-progress and error state on the button, final flip after the action. |
| add to Installed_View | `InstalledTreeProvider` re-reads `repository.snapshot()` on `repository.onDidChange`; `GoModRepository` reloads go.mod on file-watcher events (300 ms debounce) and on `refreshAll()`. | Call `repository.refreshAll()` right after the Go command so the view updates without waiting for the watcher. |
| Installed badge in Search_View | `SearchViewProvider` posts `{type:'installed', modules}` on `ready` and on every `repository.onDidChange`; `render.ts` badges results with `isInstalledPackage`. | Nothing in the Search code. A test pins the end-to-end path. |
| uninstall + inverse | same as above | `findInstalledModule` to resolve which go.mod `require` line to drop. |

Because every view derives from go.mod, there is deliberately NO parallel "installed" state to keep in sync. The sync path is: Go command changes go.mod -> `repository.refreshAll()` -> `repository.onDidChange` -> {Installed tree refresh, Search `installed` message, `detailController.refreshInstalled()`}.

### Facts that shaped the decisions

- Probed with the local toolchain (go 1.26.3), outside the repo:
  - `go get -- github.com/pkg/errors` adds `require github.com/pkg/errors v0.9.1 // indirect` (indirect because nothing imports it yet). The Installed view already lists indirect requires (`goModParser` drops comments), so the package appears.
  - `go get -- os` exits 0 and changes nothing. So stdlib paths must be refused before running Go, or the UI would report success and keep showing Install.
  - `go mod edit -droprequire=<module>` removes exactly that line, works offline, and exits 0 even when the module is absent.
  - `go get -- <unresolvable>` fails with a readable message on stderr and exit 1; `--` is accepted by `go get`.
  - PowerShell mangles `-flag=a.b.c` (splits at `.`); Node `execFile` with an args array does not. Use `execFile`, never a shell, and never build a command string.
- `src/core/installedMatch.ts`: `collectInstalledModulePaths(snapshot)` and `isInstalledPackage(path, Set)`. The package path in the Detail tab can be a sub-package (`github.com/spf13/cobra/doc`, opened from Search) or the module path (opened from the Installed view via `SHOW_DETAIL_COMMAND`). Uninstall must therefore map the package path to the module `require` line using the same prefix + `/vN` rules.
- `FolderGoModState` (`src/core/installedModel.ts`): only `kind:'parsed'` has `dependencies` and `goModPath` (an fsPath of go.mod); `folderName`, `modulePath` are available for labels.
- `src/vscode/goModRepository.ts`: `snapshot()`, `onDidChange`, `refreshAll(): Promise<void>` (cancels debounces, reloads all folders, fires `onDidChange` per folder before resolving).
- `src/core/detailController.ts`: `DetailControllerDeps {client, output, isInstalled, timers?, now?, timeoutMs?}`, `setState` emits `{type:'state'}`, `refreshInstalled()` emits `{type:'installed'}` only on change, `requestInstall/requestUninstall` are the stub, `reset()`/`dispose()`. `show(sameRunningPath)` early-returns, so a busy state survives re-clicks of the same package.
- `src/vscode/detailPanelManager.ts` already routes `install`/`uninstall` webview messages to `controller.requestInstall/requestUninstall` (parser `parseDetailMessage` already accepts both). No change needed there.
- `src/webview/detail.ts` rebuilds header+main on every `state` message (known, non-blocking issue 1 in `detail-tab-review.md`: `renderedDetail !== detail` is identity compare). Busy/error updates therefore must NOT travel as `state` messages or the button would be recreated and lose keyboard focus on every action update. They use a new lightweight `action` message (like the existing `installed` message).

## 2. Decisions (rationale in 1-2 sentences each)

1. **Installed state is derived from go.mod only.** After a Go command the host calls `repository.refreshAll()` and recomputes `installed` from the snapshot; it never flips the flag optimistically. Rationale: three views stay consistent by construction, and a "successful" command that did not change go.mod is detected instead of hidden.
2. **Install = `go get -- <path>`** in the chosen workspace folder; **Uninstall = `go mod edit -droprequire=<module>`**. Rationale: `go get` is the toolchain's own way to add a requirement (resolves the version, updates go.sum). `-droprequire` removes exactly the line the Installed view shows, offline and fast, whereas `go get mod@none` can downgrade unrelated dependents and needs the network. `GOWORK=off` is set in the child env so the go.mod we edit is the one the Installed view reads (the repository reads only `<folder>/go.mod`).
3. **Uninstall of a sub-package removes its whole module** (`github.com/spf13/cobra/doc` drops `github.com/spf13/cobra`), because that is the only entry the Installed view has. The output channel line states both the requested path and the module.
4. **Stdlib / non-module paths are refused before running Go**: a path whose first segment has no `.` is not installable (`os`, `net/http`). Rationale: `go get -- os` exits 0 and does nothing (probed). Also refuse paths starting with `-` (flag injection; `isValidImportPath` allows a leading `-`).
5. **Target folder**: candidates are workspace folders whose go.mod is `parsed`. Install: all of them. Uninstall: only folders that require the module. One candidate -> use it. Several -> `vscode.window.showQuickPick` (injected as `pickFolder`); Esc cancels silently with no state change. No candidate -> error "No go.mod found..." (install) / "not required by any go.mod" (uninstall). Rationale: avoids silently editing the wrong root in multi-root workspaces without inventing a settings surface.
6. **Serialisation**: `PackageActions` runs one Go command at a time (promise chain). Concurrent `go get` on one go.mod would race. The controller tracks pending actions per path (Map), so the busy state follows the package even if the user opens another package and comes back.
7. **Busy UI**: button gets `aria-disabled="true"` plus label "Installing…"/"Uninstalling…", clicks ignored in the webview and in the controller. `aria-disabled` (not `disabled`) so keyboard focus is not dropped. Rationale: prevents double-click and keeps focus.
8. **Failure UI**: inline `role="alert"` message with Go's first meaningful stderr line in a new `#detail-action-error` region under the header, full output in the "Goget Manager" output channel, button returns to its previous label, nothing else changes. No toast popups (the user is looking at the tab). Cancellation (QuickPick dismissed) shows nothing.
9. **Protocol**: add `busy?`/`actionError?` to `DetailViewModel` (so a re-created webview gets them in the `ready` snapshot) and a new host->webview message `{type:'action', installed, busy?, error?}` (updates only the button and the error region). The existing `{type:'installed'}` message and `parseDetailMessage` stay unchanged.
10. **Timeout**: Go commands time out after 180 s (first-time `go get` can be slow) and are killed; the failure text says it timed out. Output captured to a 64 KiB cap.
11. **Search_View not resolved / hidden**: no code change. `SearchViewProvider` posts `installed` only to a resolved view and re-sends the full set on `ready` (and the webview is `retainContextWhenHidden`), so a view resolved later is correct on first paint. A test pins this.
12. **Out of scope**: `go mod tidy`, `go mod init` when there is no go.mod, version selection, `go.work`, per-folder badges, confirming module-wide removal. Fixing the pre-existing identity-compare issue in `detail.ts` is NOT part of this task (the design above avoids depending on it).

## 6. Edge cases covered and where
